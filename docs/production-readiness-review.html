Orbit HR · Engineering review

Production readiness review and launch plan

A senior-level read of the Orbit HR codebase as it stands today: what is solid, what would break or leak in production, the order to fix it in, and how the system should run once it is live.

Reviewed 5 Sep 2026 Scope web/ (Next.js 16) · api/ (NestJS 12 + Prisma 6 + Postgres 16) · docs/ Reviewer role Tech lead / project manager
Not yetProduction verdict

The foundation is good and the backend design is right. Multi-tenant scoping from the JWT, a clean module split, validated DTOs, hand-written migrations, and unusually honest docs. That is more than most six-session projects have.

But it cannot ship yet. There is no version control, one endpoint allows a cross-tenant write, read access ignores roles entirely, and four of the five screens still render mock data. Six focused weeks closes the gap. The plan below is ordered so each week reduces real risk, not just adds features.

2. Findings that matter

Verified by reading the code, ordered by how badly they would hurt a paying customer. Each one names the fix.

Critical

No version control

There is no .git directory. Every change so far exists only as files on a synced desktop. One bad sync or a mistaken delete loses the project, and nothing downstream (CI, review, deploys, rollback) is possible without it.

Fix: git init today, push to a private GitHub repo, protect main, require pull requests. Move the working copy out of OneDrive afterwards so the sync client stops fighting node_modules and .next.
Critical

Cross-tenant write through attendance upsert

The direct upsert endpoint takes employeeId from the request body and never checks it belongs to the caller's tenant. A manager in tenant A who knows an employee UUID in tenant B can create or overwrite that person's attendance. The same unchecked-ID pattern exists for managerId when creating or updating an employee.

api/src/attendance/attendance.service.ts · upsert() · api/src/employees/employees.service.ts · create() and update()
Fix: resolve every foreign ID through a tenant-scoped lookup before writing. Add an e2e test that registers two tenants and proves the write is rejected. Longer term, enable Postgres row-level security as the backstop the docs already say is missing.
High

Reads ignore roles

Roles only guard create, update, approve and reject. Any authenticated EMPLOYEE can list the whole company with phone numbers, read every leave request including the reason text, and fetch any colleague's leave balance. In HR software that is a privacy incident, and under GDPR or India's DPDP Act it is reportable.

GET /employees · GET /leave · GET /leave/balance/:employeeId
Fix: define a visibility rule per role. EMPLOYEE sees self and a public directory subset (name, title, department). MANAGER sees direct reports. HR and ADMIN see the tenant. Apply it inside the service, not the controller, so every caller inherits it.
High

Managers can approve anyone, including themselves

Approval is gated by role only. A MANAGER can approve any request in the tenant, and nothing stops them approving their own. The approval also runs as two separate writes (status update, then balance increment), so a failure between them leaves the balance wrong. There is no check that the request fits the remaining balance.

api/src/leave/leave.service.ts · decide()
Fix: wrap in $transaction; require the approver to be the employee's manager or HR/ADMIN; reject self-approval; reject when days exceeds the remaining balance.
High

Session and auth hardening

The JWT lives in localStorage for 24 hours with no refresh, no revocation, and no way to log out server-side. Login and register have no rate limiting, so password guessing and tenant-spam are free. There is no email verification, password reset, or invite flow, so the only way to add a login is the seed script. The example secret is a placeholder string.

web/src/lib/auth-context.tsx · api/src/auth/* · api/.env.example
Fix: short-lived access token (15 min) in an httpOnly, SameSite cookie plus a rotating refresh token stored hashed in Postgres. Add @nestjs/throttler and helmet. Build the invite flow (ADMIN/HR creates a User for an existing Employee, sends a set-password link). Generate the production secret with openssl rand -base64 48.
High

"Today" is the server's today

Attendance computes the current day and the LATE cutoff from the server's local clock. On a UTC container, a Bengaluru employee clocking in at 9 AM is recorded at 3:30 AM UTC, and anyone clocking in before 5:30 AM IST lands on yesterday's row. The seeded data has employees in six time zones.

api/src/attendance/attendance.service.ts · startOfToday(), clockIn()
Fix: add timezone to Tenant (later to Employee), compute the business date and LATE cutoff in that zone with a library such as date-fns-tz, and make the cutoff a tenant setting rather than a hardcoded 10:00.
High

Departments are hardcoded in the frontend and free text in the backend

The department landing page is statically generated from six mock names and calls notFound() for anything else. Login redirects to /d/{department}. The moment a real tenant creates an "Operations" employee and gives them a login, they get a 404 after signing in.

web/src/app/(app)/d/[department]/page.tsx · web/src/app/login/page.tsx · prisma Employee.department
Fix: add a Department table (tenant-scoped, with a slug), make the landing page dynamic and fetch from the API, and let tenants define their own list in settings.
Medium

Four of five screens are mock

Dashboard, Employees, Attendance and Leave import from mock-data.ts. Approve and reject on the leave board mutate React state. The dashboard greets "Girija" and says "Sep 2" as string literals, and the sidebar hardcodes "Acme Inc." regardless of tenant. Only the header identity and login are real.

Fix: Phase 2 below. Adopt TanStack Query, add the two aggregate endpoints the dashboard needs, and replace one screen at a time in the order Employees, Attendance, Leave, Dashboard.
Medium

Leave arithmetic is naive

Days are counted inclusively across calendar days, so a Monday-to-Friday request costs 5 and a Saturday-to-Sunday one costs 2. There is no holiday calendar, no accrual period, and no annual reset, so balances only ever go up.

Fix: a LeavePolicy per tenant (working days, holidays, entitlements) and a LeaveBalance row per employee per period. Compute days server-side from the policy and return it to the UI before submit.
Medium

Tests do not reflect the app

The e2e spec still requests GET / and expects "Hello World!", but the only route is GET /api/health. Running npm run test:e2e fails before any real behaviour is exercised. The four business modules have zero tests, and the end-to-end verification in the changelog was done by hand.

Fix: delete the stale spec. Add supertest e2e tests against a throwaway Postgres (Docker service in CI) covering the flows the changelog already verified manually, plus the tenant-isolation cases above. Aim for the tests to be the thing that proves the isolation, not a session transcript.
Medium

Housekeeping

  • Three prisma-composer skill folders (.agents, .cursor, .devin) left over from the wrong Prisma install. Delete them.
  • tsconfig.build.tsbuildinfo sits in the source tree. Ignore it.
  • List endpoints have no pagination. Fine for 15 rows, not for a 2,000-person tenant.
  • No request logging, no request ID, no structured errors. Debugging production will be blind.
  • User.email is globally unique, so one person can never belong to two tenants (a contractor, an auditor). Acceptable for v1, but decide it consciously and document it.
  • The seed uses Math.random() for balances, so two seeded environments differ. Make it deterministic.

3. Roadmap to production

Seven phases, in order. Each ends with a gate you can check, not a feeling. Estimates assume one full-time engineer.

0

Foundations

Week 1, first two days
  • Initialise git, push to GitHub, protect main, all work through pull requests.
  • Add a root package.json with workspaces (or keep two apps but one CI file) so lint, typecheck, test, build run from the root.
  • GitHub Actions: on every PR run lint, TypeScript check, unit tests, and both builds. Spin up Postgres as a service container and run prisma migrate deploy so migrations are validated on every change.
  • Delete the composer leftovers, fix the stale e2e spec, ignore build info files.
  • Pin Node to 22 LTS with .nvmrc and engines. Prisma stays pinned at 6.19.x as the docs already warn.
Gate: a PR that breaks the build or a migration cannot merge.
1

Security and correctness

Week 1 to 2
  • Tenant-scope every foreign ID (employeeId, managerId) before writing.
  • Role-aware reads: visibility rules for employees, leave, balances. Manager-scoped approvals, no self-approval, balance check, transactional decide.
  • Move the session to an httpOnly cookie with refresh rotation. Add throttling and helmet. Lock CORS to the real web origin.
  • Invite flow and password reset, with transactional email through Resend or Postmark.
  • Tenant timezone and a configurable late cutoff.
  • Enable Postgres row-level security keyed on a session variable Prisma sets per request. This is the safety net for the next missed tenantId.
Gate: an e2e suite proves two tenants cannot read or write each other's data through any endpoint, and an EMPLOYEE cannot read a colleague's leave reason.
2

Wire the frontend to the API

Week 2 to 4
  • Adopt TanStack Query for fetching, caching and optimistic updates. Generate typed API clients from the DTOs (or share a packages/contracts type module) so the two apps cannot drift.
  • Replace screens in order of value: Employees (list, profile, create, edit), Attendance (today, clock in and out for self), Leave (request, approve, reject against the real API), then Dashboard.
  • Add the two aggregate endpoints the dashboard needs: GET /dashboard/stats and GET /attendance/trend?days=7. Never compute aggregates in the browser from full lists.
  • Department landing page becomes dynamic and API-backed. Tenant name and greeting come from /auth/me.
  • Delete mock-data.ts when the last import is gone. That deletion is the milestone.
Gate: grep -r mock-data web/src returns nothing, and a fresh tenant registered through the UI can run a full leave cycle end to end.
3

Complete the data model

Week 4 to 5
  • Department table, tenant-scoped, editable in settings.
  • LeavePolicy with working days, public holidays, entitlements per type. LeaveBalance per employee per year.
  • AuditLog for every write that touches a person: who, what, when, before and after. HR customers will ask for this in the first demo.
  • Soft delete for Employee (deletedAt) so offboarding keeps history.
  • Cursor pagination on every list endpoint.
Gate: every migration in the folder applies cleanly to a copy of the staging database.
4

Testing you can trust

Runs alongside phases 1 to 3, closes in week 5
  • Unit tests for service logic: leave day calculation, balance checks, timezone day boundaries, role visibility.
  • Supertest e2e per module against a real Postgres in CI, seeded per test file.
  • Playwright smoke suite for the five critical paths: register, invite and accept, clock in, request leave, approve leave. Run on every deploy to staging.
Gate: CI is green, and the smoke suite runs against staging automatically.
5

Infrastructure and deployment

Week 5 to 6
  • Web: Vercel. It is what Next.js 16 is built for, and you keep the webpack build flag you already need.
  • API: a multi-stage Dockerfile (build, then a slim node:22-alpine runtime running dist/main), deployed to Railway, Fly.io or Render. Two instances minimum behind their load balancer.
  • Database: managed Postgres with automated backups and point-in-time recovery. Neon or Supabase for speed, RDS if the company already has AWS. Never Docker Compose in production.
  • Migrations: prisma migrate deploy runs as a release step before the new API version receives traffic, never at container start.
  • Secrets: platform environment variables only. No .env files on servers.
  • Staging environment that mirrors production, with its own database, seeded with the demo tenant.
  • Custom domain, TLS, and CORS restricted to https://app.yourdomain.
Gate: a merge to main reaches staging with no manual steps, and a tagged release reaches production with one approval click.
6

Observability and launch

Week 6
  • Structured JSON logs (pino) with a request ID and the tenant ID on every line. Ship them to the platform's log drain or Better Stack.
  • Sentry in both apps, with the tenant and user role attached to every event.
  • /api/health must hit the database, and the platform must use it for readiness. An uptime monitor pings it every minute.
  • Restore a backup into staging once, on purpose, and time it. A backup you have never restored is a hope.
  • Load test the list and dashboard endpoints at a 2,000-employee tenant size.
  • Privacy policy, data retention rules, and an internal runbook for "a customer asks us to delete their data".
Gate: the launch checklist in section 6 is fully ticked.

5. Delivery pipeline

What happens between a developer's push and customers seeing the change.

Rule that makes the pipeline safe: every migration must be backwards compatible with the currently running API. Add a column now, start writing it in the next release, drop the old one two releases later. This is what lets you roll back code without restoring a backup.

6. Launch checklist

Tick every line before the first external tenant. Owner: whoever is on call that week.

  • Repository on GitHub with protected main and required CI.
  • Tenant-isolation e2e tests pass for every endpoint that accepts an ID.
  • Role visibility rules documented and tested for all four roles.
  • Session in httpOnly cookie, refresh rotation, logout revokes.
  • Rate limiting on login, register, invite, and password reset.
  • Production JWT secret generated, stored only in platform secrets, rotated at least once to prove the process works.
  • No import of mock-data.ts remains in web/src.
  • Managed Postgres with daily backups and PITR, and one restore rehearsed.
  • Health check hits the database and gates readiness.
  • Sentry receiving events from both apps, alert routed to a person.
  • Structured logs with request ID and tenant ID, retained 30 days.
  • Load test at 2,000 employees: list and dashboard endpoints under 500 ms p95.
  • Privacy policy, retention policy, and data-deletion runbook written.
  • Seed passwords and demo tenant do not exist in production.

8. Your first week, concretely

  1. Monday: git init, push, branch protection, CI skeleton. Delete composer leftovers and the stale e2e spec.
  2. Tuesday: tenant-scope the attendance upsert and employee manager ID. Write the two-tenant e2e test first, watch it fail, then fix.
  3. Wednesday: role visibility rules for the three read endpoints. Transactional, manager-scoped leave approval.
  4. Thursday: throttler, helmet, cookie-based session, CORS lock. Generate a real secret.
  5. Friday: tenant timezone, dynamic department page, and a Dockerfile for the API so staging can exist next week.

By Friday the app is safe to put in front of an internal user on a staging URL. The following four weeks are about replacing mock data and building the operational scaffolding around it.
